# Design: LiteRT.js WebNN Demo Site

Generated by /office-hours on 2026-08-17
Branch: main
Repo: ibelem/webnn-litert
Status: APPROVED
Mode: Builder

## Problem Statement

There is no demo site for LiteRT.js on WebNN. Microsoft's `webnn-developer-preview`
proves the pattern works for ONNX Runtime Web — a home page, per-model demo pages,
URL-switchable backends — but nothing equivalent exists for `.tflite` models via
LiteRT.js, and LiteRT.js is the only web runtime that can target WebNN NPU from a
TFLite model today.

Build that site: a home page, per-demo detail pages, every demo runnable on WebGPU,
WebNN GPU, and WebNN NPU (selectable by URL parameter), each reporting
`loadAndCompile()` time and inference time.

The catch found during this session: LiteRT.js reports success while silently running
part or all of a model on WASM CPU, so a naive demo site would publish CPU numbers
under a WebNN label. The site's real job is therefore narrower and more valuable than
"show demos" — it is to show demos *with proof the requested backend actually ran*.

## What Makes This Cool

Three numbers next to three delegation badges, on the same input, on one screen.

Every ML demo site shows one backend at a time behind a dropdown, which asks the viewer
to remember what the last number was. A side-by-side view makes the WebNN case in a
single screenshot — and the delegation badge makes it a claim someone can actually
trust, which is rarer than it should be.

The lateral insight: LiteRT.js's own fallback behavior makes a bare millisecond counter
*actively misleading*, so inverting the usual hierarchy — delegation truth first,
latency second — turns a routine demo site into the reference people cite.

## Constraints

- **Target: Chrome M153+ stable and Chrome Canary.** No other browsers, no legacy
  paths, no version-gating UI. Modern platform APIs (`OffscreenCanvas`, top-level
  await, recent WebGPU) are all fair game.
- **JSPI is always available and always required.** `loadLiteRt(wasmPath, {jspi: true})`
  is mandatory for WebNN; M153 is far past JSPI's Chrome 137 debut. The consequence is
  significant — see *Receipts* below.
- **LiteRT.js is loaded from CDN at runtime, not bundled.** Default `2.5.3`, overridable
  via `&litertjs=x.x.x`. It is a devDependency for *types only* (`import type`); the
  runtime comes from esm.sh. See *Runtime loading* below.
- **WebNN is `[experimental]` in `@litertjs/core@2.5.3`** and half-wired in the TS
  layer (see Premise 2).
- **COOP/COEP required** for threaded WASM. LiteRT's own dev servers set
  `Cross-Origin-Embedder-Policy: require-corp`
  (`reference/litert/litert/js/apps/model_tester/serve.js:59`). Resolved by hosting on
  Vercel.
- **All five models are mirrored under the `webnn/` HuggingFace org** — see
  `docs/model.md` for the full mapping of upstream demo → original source → HF URL.
  No `convert_model.py` step, no dependency on Google's GCS bucket or Qualcomm's repo,
  and model versioning sits under HF revisions.
- **NPU availability is hardware-gated, not browser-gated.** A current-Chrome user on a
  machine without an NPU still cannot run `webnn-npu`, and `isWebNnSupported()` does not
  report which `devicePreference` values will resolve. The honest answer may only be
  discoverable by attempting the compile and reading the receipt.
- **Reference trees are gitignored** (`.gitignore` contains `reference/*`), so nothing
  in `reference/` ships. Code must be ported, not imported or symlinked.

## Premises

Agreed during the session:

1. **The site's primary job is delegation truth, not speed.** A silent CPU fallback must
   be impossible to mistake for a WebNN run. Every latency number carries a receipt.
2. **WebNN in `@litertjs/core@2.5.3` needs a spike before the site is built around it.**
   `packages/core/src/accelerator_types.ts:22` exports
   `ACCELERATORS = ['webgpu', 'wasm']` with no `'webnn'`, and
   `AcceleratorDefaultTensorBufferType` (`:32`) has no `webnn` key — so tensor-copy
   defaults on the WebNN path are undefined. Meanwhile `wasm_binding_types.ts:107`
   accepts `'webnn'` and `litert_web.ts:195` handles it.
3. **The backends are not peers** — but the gate is hardware, not browser version.
   The UI must detect and *explain* rather than offer a dropdown that fails.
4. **Port the metrics schema from `ibelem/web-ai-run`**, don't redesign it: it already
   records `load_and_compile_ms`, `first_inference_ms`, `time_to_first_ms`,
   average/median/best/p90 and `throughput_fps`, with warmup runs timed but excluded
   from statistics.
5. **Model sourcing is solved** via `docs/model.md`, so "make the demos work" reduces to
   porting pre/post-processing and building a uniform backend selector — only
   `selfie_multiclass` currently knows about WebNN.
6. **Hosting must set COOP/COEP** — resolved: Vercel.

## Approaches Considered

### Approach A: Port the upstream demos, bolt on a shell
Copy the five demos, retrofit a selector and metrics panel onto each. **Rejected:** five
near-duplicate codebases where uniformity depends on discipline rather than structure —
reintroducing the exact credibility risk Premise 1 exists to prevent.

### Approach B: One app, demo registry, one runner
Single app; one runner owns backends, timing and receipts; demos are registry entries.
**Chosen as the substrate, not the endpoint** — sound, but keeps the
one-backend-at-a-time dropdown that makes the WebNN comparison weaker.

### Approach C: Worker-based side-by-side comparison — **CHOSEN**
Approach B's registry and single-runner architecture, plus inference in a Web Worker,
plus a default view showing all backends on the same input: one input, N outputs, N
latencies, N delegation badges.

## Recommended Approach

**Approach C**, chosen by the user over the recommended B. The rationale that carried
it: the side-by-side view is the product, not a feature — a dropdown asks the reader to
hold a number in their head; a row of results makes the argument in one screenshot. And
web-ai-run's worker architecture already exists to port, so the marginal cost of the
worker is far lower here than for a generic team.

C strictly contains B, so the registry and single runner survive and Premise 1's
receipts stay uniform by construction.

### Stack: TypeScript + Vite, no UI framework

Considered and rejected, in order:

- **Next.js** — a server framework for a site with no server work. Nothing here *can* be
  server-rendered: every page depends on capability detection and a WASM module that
  exists only client-side. Full complexity, zero benefit.
- **React** — no technical blocker, but no ecosystem need either (no routing library, no
  state management, no data fetching), and it would add a third framework across the
  author's projects.
- **SvelteKit** — the strongest alternative, since `web-ai-run` already ships SvelteKit 5
  + Vite + `adapter-vercel`. Rejected in favour of zero UI dependencies.
- **Lit** — upstream's own direction (`model_tester`, `depth_anything`, `real_esrgan` all
  use it) and Shadow DOM would have enforced style isolation at the platform level.
  Rejected on author preference.

The deciding argument for vanilla: the framework would only serve the *shell*, and the
shell is six components. Demos are already framework-agnostic by contract. A reference
site for two moving specs benefits from still building untouched in three years.

Vite still handles the build, dev-server isolation headers, worker bundling and
multi-page output — only the UI framework is dropped.

Built and verified as of this revision (`npm run build` green: tsc + stylelint + vite):

**M1 still to add:** `runner/litert.worker.ts` (wrapping `measure.ts`, one worker per
backend), `runner/scheduler.ts` (the measurement token), `demos/` with the per-demo

Note there is no `public/wasm/` — wasm comes from jsDelivr at runtime, keyed by
`&litertjs=`, so nothing is vendored.

**Vercel compatibility verified**, not assumed:

- Static only; no serverless functions, no SSR. `outputDirectory: dist`.
- **MPA, not SPA.** `cleanUrls: true` maps `debug.html` → `/debug`, so every page is a
  real prerendered document with its own title and meta. M1 generates per-demo entries
  into the same input map from the registry, so home and detail pages cannot diverge.
- The `import(/* @vite-ignore */ …)` of esm.sh **survives the production build** as a
  runtime string (confirmed in `dist/assets/debug-*.js`), and `@litertjs/core` is
  genuinely absent from the bundle — types-only worked.
- Both isolation headers are set identically in `vercel.json` and `vite.config.ts`, so
  dev and production agree. The debug page renders a visible banner when
  `crossOriginIsolated` is false, rather than silently publishing a single-threaded CPU
  baseline as if it were threaded.

### Chrome vs stage — the element-identity rule

Every demo page has two zones with opposite properties:

**Chrome** is owned by the shell: backend picker, receipt badges, metric rows, status,
console. It is a pure function of run state and holds nothing, so it can be rebuilt on
every state transition.

**Stage** is owned by the demo: created once per backend, never replaced. It holds state
the shell did not put there — `<canvas>` pixels, a live `MediaStream` on `<video>`, an
`<img>` pointing at a `createObjectURL` blob, a file input's selection, focus, scroll.

The split works because all the churn is in the chrome (queued → compiling → warmup →
measuring → done/failed, per backend) and all the statefulness is in the stage. Naive
full re-render is therefore safe, **provided it is never pointed at a stage**.

Not a canvas rule: `mobilenetv2` uses no canvas at all (`<img>` input, text output) and
still breaks if its region is rebuilt, because it would lose the uploaded image and the
file selection.

```ts
interface DemoDefinition {
  slug: string;
  title: string;
  model: { url: string; labels?: string };   // HF URLs from docs/model.md
  backends: Backend[];

  // called once per backend. The demo builds whatever DOM it needs
  // inside `container` and returns its own handle.
  mountStage(container: HTMLElement): Stage;

  preprocess(input: DemoInput): Tensor;
  postprocess(out: Tensor): DemoOutput;
  render(out: DemoOutput, stage: Stage): void;
}
```

`Stage` is whatever the demo returned — a 2D context for segmentation, a `<ul>` for
mobilenetv2's labels, a before/after pair for real_esrgan. The shell hands over a
container and never looks inside again.

### Backend mapping

| URL param | Compile options |
|---|---|
| `?backend=webgpu` | `{accelerator: 'webgpu'}` + `setWebGpuDevice(device)` |
| `?backend=webnn-gpu` | `{accelerator: 'webnn', webNNOptions: {devicePreference: 'gpu'}}` |
| `?backend=webnn-npu` | `{accelerator: 'webnn', webNNOptions: {devicePreference: 'npu'}}` |
| `?backend=wasm` | `{accelerator: 'wasm'}` — opt-in CPU baseline |

Comma-separated for comparison: `?backend=webnn-npu,webgpu`. WASM/CPU is an opt-in
baseline rather than a peer in the default view: it gives accelerated numbers a scale
without making the landing experience about CPU.

### Runtime loading and version selection

LiteRT.js is fetched from CDN at runtime, so any published version can be exercised
without a rebuild. Pattern ported from `web-ai-run`'s `inference.worker.ts`:

```ts
const litert   = await import(/* @vite-ignore */ `https://esm.sh/@litertjs/core@${v}`);
const wasmRoot = `https://cdn.jsdelivr.net/npm/@litertjs/core@${v}/wasm`;
```

**Two CDNs deliberately** — esm.sh resolves bare specifiers into real ESM for the module
graph; jsDelivr serves the raw `wasm/` assets. Not interchangeable.

Three non-obvious requirements, all learned from the web-ai-run implementation:

1. **`locateFile` must be set on `globalThis.Module`** before loading —
   `loadLiteRt(wasmRoot)` alone does not redirect Emscripten's own `.wasm` fetches.
2. **The threaded pthread host script must be re-hosted same-origin** as a blob URL:
   fetch `${wasmRoot}/litert_wasm_threaded_internal.js` as text, wrap in a `Blob`, pass
   as `mainScriptUrlOrBlob`. This is what makes threaded WASM work cross-origin under
   COEP.
3. **Guard on API existence** (`if (litert.loadLiteRt)`) — older published builds lack
   exports, so the runner probes capability rather than assuming it.

Load mode is derived from the backend: `jspi: true` for WebNN and WebGPU,
`threads: true` for the CPU baseline, `threads: false` otherwise.

**Version parameter.** Default `2.5.3`. Override with `&litertjs=x.x.x`, e.g.
`?backend=webnn-npu&litertjs=2.5.0`.

**The version string is validated before it reaches `import()`.** Interpolating raw user
input into a module URL is arbitrary module execution — `&litertjs=1.0.0/../../@x/evil`
walks out of the package and `import()` runs whatever resolves. Strict semver test at
minimum; a known-good allowlist preferred, since a version dropdown is wanted anyway and
arbitrary versions mostly produce broken pages.

```ts
const VERSION_RE = /^\d+\.\d+\.\d+(-[a-z0-9.]+)?$/;
```

### One worker per backend

Consequence of how LiteRT.js manages state, not a performance choice.

`loadLiteRt` mode and loaded version are **module-global per worker**, and switching
either requires `unloadLiteRt()` + reload (web-ai-run guards exactly this). Since WebNN
and WebGPU need `jspi: true` while the CPU baseline wants `threads: true`, a JSPI-mode
and a threaded-mode LiteRT cannot be alive in one worker simultaneously. `globalThis.Module`
is also a global that two concurrent loads would race on.

So: **one worker per backend**, each owning its own module-global at the right mode and
version. All stay compiled and ready; `scheduler.ts` still grants the measurement token
to one at a time so only one *runs*. This also lines up with one stage per backend, and
avoids refetching wasm on every backend switch.

### Three measurement axes

**Backend × browser channel × LiteRT.js version.** Never aggregate across any of them —
each is a grouping key, not a footnote. Every result set records all three.

### Receipts — reworked for a JSPI-always target

This is the section the Chrome M153+ decision changed most. From `litert_web.ts:198`:

```ts
if (acceleratorRequested && !compiledModel.isFullyAccelerated) {
  if (isJspiSupported()) {
    console.warn(`Model not fully compiled for ${accelerator}. Partially delegating to WASM.`);
    // keeps the model. options.accelerator still says 'webnn'.
  } else {
    compiledModel.delete();
    return this.loadAndCompile(modelData, {accelerator: 'wasm'});  // honest, at least
  }
}
```

Every target user is on the JSPI branch. Therefore:

- The **total fallback never fires**, so the failure that would have been visible — a
  model coming back relabelled `wasm` — cannot happen.
- What happens instead is **partial delegation**: `options.accelerator` still reads
  `'webnn'` while an unknown fraction of the graph runs on WASM CPU. It reports success
  and returns a number.
- **`effective_accelerator` is therefore useless as a signal.** It always equals the
  request. Do not ship it as evidence.

Two signals remain, and they carry the entire credibility argument:

1. `compiledModel.isFullyAccelerated`
2. LiteRT's `console.warn`, emitted nowhere else — which makes porting
   `model_tester/src/console_mirror.ts` **load-bearing infrastructure**, not
   observability polish. It is half the remaining evidence.

Design consequence: **`isFullyAccelerated === false` is the expected outcome for WebNN
runs, not an edge case**, since op coverage is still filling in. Design the
partially-delegated result card *first* and the fully-delegated one second. A partial or
failed delegation must never render its latency as a headline number.

### Browser channel is part of the measurement

The site spans two channels, and Canary and M153 stable are not necessarily the same
WebNN implementation. So:

- Tag every result set with channel + full version
  (`navigator.userAgentData.getHighEntropyValues(['fullVersionList'])`).
- **Never aggregate across channels.** Channel is a grouping key, not a footnote.
- A demo that is *partially* delegated on stable and *fully* delegated on Canary is the
  most interesting datapoint the site can produce — a shipping-progress signal for the
  WebNN implementation. Surface it deliberately. (Post-M4 feature, not M1.)

### Measurement contention

Running backends concurrently would have them contend for memory bandwidth and thermal
headroom and corrupt each other's timings — the main risk against Approach C.

**Resolution: measure serially, present simultaneously.** `scheduler.ts` grants a
measurement token to one backend at a time; each runs its full lifecycle (load+compile →
warmup → N iterations) exclusively, and results reveal progressively into the
side-by-side layout. The UI states "measured sequentially" so the presentation never
over-claims. An optional `?mode=race` runs concurrently for effect and marks all timings
non-comparable.

### Demo site, not a benchmark

Load-bearing framing, restated because the architecture above can easily be built into
the wrong product. `web-ai-run` is the benchmark tool and already exists; this is not it.

The hero of every page is the **visual output** — segmentation over a webcam, a depth map,
an upscaled image. Metrics are receipts: small, secondary, present so the visual claim is
trustworthy. Not the content.

No p90/best/average tables, no iteration and warmup inputs, no "Run" button as the primary
interaction, no dense numeric grid carrying the page's visual weight. The compare view is
**three live outputs side by side**, each with one latency figure and a badge underneath —
not three rows of a table. Same input, three pictures, three numbers.

### Metrics: compute all, display little

**Compute** (ported from web-ai-run's `computeMetrics`): `load_and_compile_ms`,
`first_inference_ms`, `time_to_first_ms`, `average_ms`, `median_ms`, `best_ms`, `p90_ms`,
`throughput_fps`, raw `inference_times[]`. Warmup timed but excluded from statistics.
Costs nothing, goes to the console, available for a future export or a LiteRT bug report.

**Display on the page — exactly two metrics:** `loadAndCompile` time (once per backend,
and it stays visible, because it's the number that shows what WebNN costs up front: ~2000 ms
vs WebGPU's ~35 ms) and inference time (latest run, updating live).

**Everything else is `console.log` only:** average, median, best, p90, throughput_fps,
time_to_first_ms, first_inference_ms, raw `inference_times[]`, effective accelerator, input
shapes, browser channel and version — one object per backend, copy-pasteable into a bug
report. FPS is in that list deliberately: it's `1000 / average` and adds nothing beside a
live inference figure.

The **delegation badge is not a metric** and is exempt — it stays on the page always. It's
the receipt that makes the two visible numbers trustworthy.

### What is inside the measured region

One choice, applied identically to all four backends: **input upload → `run()` → output
readback.**

The readback is mandatory. WebGPU submits asynchronously, so `run()` resolves once
commands are enqueued rather than executed — the first M0 run reported **0.2 ms /
3055 fps** for MobileNetV2 on WebGPU before this was fixed. WebNN under JSPI appears
genuinely synchronous through `run()`, but the readback applies everywhere anyway, because
uniformity is what makes the figures comparable. Upload is included because a webcam demo
really does upload a fresh frame per inference.

The metric is therefore **time to usable output**, not kernel time. Differs from
web-ai-run (which excludes upload and reads back only on WebGPU), so numbers are not
comparable between the two projects.

### Design system

Specified in full in [`DESIGN.md`](../../DESIGN.md), implemented in `src/ui/tokens.css`.
Summary of the decisions that affect architecture:

- **Identity derived from webnn.io / `ibelem/webnn-docs`** — Instrument Sans 700 headings,
  Geist body, Intel One Mono for code and all numbers; the navy↔cyan primary flip; the
  accent ramp. Family resemblance is deliberate: same audience. `@material/web` (used by
  `model_tester`) is explicitly excluded — it's what would make this read as another
  Google demo page.
- **Token architecture diverges from the source.** `webnn-docs` overrides component
  selectors for dark mode; here dark mode swaps token *values* only, in three states
  (`:root`, `prefers-color-scheme`, explicit `.dark`).
- **Two independent colour channels**, because a result card must say both *which
  backend* and *did it run there*. Backend = hue (blue/cyan/purple, wasm neutral so the
  baseline recedes). Delegation = a reserved set (orange/pink, used by no backend, so no
  collision) plus mandatory text and a non-colour treatment.
- **Fully-delegated is the unmarked state.** Since partial delegation is the *expected*
  outcome under our target, a green checkmark for success would make the site look broken
  by default and train readers to ignore the signal. The marked state is the informative
  one — and the site gets quieter as coverage improves.
- **All measured numbers use tabular figures.** Without them digits change width as
  values update and the compare grid visibly jitters mid-run.
- **`receipt-badge` and `metric-row` take no style overrides** — load-bearing for
  credibility, not decoration.
- **stylelint bans raw hex and raw px outside `tokens.css`.** With no framework there is
  no scoping mechanism, so this is the design system's only *automated* boundary. Wire it
  in M1.
- **No Playwright, no end-to-end browser tests, no visual regression.** Project
  constraint. It also happens to fit: every page renders live inference output and live
  timings, so screenshots are non-deterministic by construction. Testing is unit tests for
  the pure parts (`computeMetrics`, version validation, param parsing, receipt
  classification), stylelint, `tsc --noEmit`, and manual verification in Chrome — which is
  unavoidable regardless, since NPU delegation depends on real hardware. Accepted
  consequence: nothing automated guards visual consistency or the live inference path.

Layout and composition are still unspecified — the compare grid needs a real pass, since
N backends side by side must work at N=2 and N=4 with stages of wildly different aspect
ratios (mobilenetv2's label list vs real_esrgan's 4× canvas).

## Open Questions

1. ~~Does the published npm package ship a JSPI WASM build with the WebNN delegate?~~
   **Resolved by CDN loading** — the question is now empirical rather than a matter of
   inspection: point `&litertjs=` at a version and read the receipt. Remaining sub-question
   is *which* published versions have a working WebNN delegate, which M0 answers by
   sweeping a few and which then seeds the version allowlist.
2. **Tensor buffer type on the WebNN path.** `AcceleratorDefaultTensorBufferType` has no
   `webnn` key, so what does a copy to a WebNN-compiled model actually do? Likely host
   memory, possibly a per-inference copy that dominates the timing.
3. **WebGPU device inside a Web Worker.** `setWebGpuDevice()` needs a `GPUDevice`, and
   upstream demos use `tfjs-interop` for pre/post processing. Confirm the worker can own
   its own adapter/device, or move pre/post to the main thread and transfer tensors.
4. **Which NPU hardware validates this?** Intel Core Ultra, Snapdragon X, both?
   `devicePreference: 'npu'` means nothing without a target device to confirm on.
5. **Does a CORS-mode fetch from HuggingFace satisfy COEP `require-corp`?** HF's
   `resolve/main` sends `access-control-allow-origin: *`, and CORS-mode fetches that
   pass the check are exempt from the CORP requirement — so it should be fine. Confirm
   against real Vercel headers in M1 before four more demos depend on it.
6. **Compare-view memory ceiling.** `real_esrgan` at 4× turns a 512px input into
   2048×2048 per backend — roughly 16 MB of canvas backing store each, ~64 MB across
   four, while four compiled models and their tensor buffers are also resident. Likely
   answer: cap comparison input resolution for upscaling demos, or let
   `DemoDefinition` declare a max comparison arity. Shows up as a tab crash on a
   mid-range laptop, not as an error message.
7. **Visual identity is undesigned.** The enforcement mechanism above keeps the site
   internally consistent but says nothing about whether the style is good or
   distinctive. `/design-consultation` would resolve this and produce `DESIGN.md`; best
   done before M1, since retrofitting tokens onto built components is the expensive
   version.

## Success Criteria

- All four backends selectable via `?backend=`, multi-backend comparison as the default
  view.
- Every displayed result carries a delegation receipt; no latency shown as a headline
  without one; partially-delegated is a visually dominant state.
- At least one demo confirmed **fully delegated to WebNN NPU** on real hardware.
- Side-by-side comparison working on at least one demo.
- Deployed to Vercel with `crossOriginIsolated === true` verified in production.
- Timing methodology identical across every demo — enforced by there being exactly one
  code path that can produce a number.

## Distribution Plan

Static site on **Vercel**. `vercel.json`:

```json
{ "headers": [{ "source": "/(.*)", "headers": [
  { "key": "Cross-Origin-Opener-Policy", "value": "same-origin" },
  { "key": "Cross-Origin-Embedder-Policy", "value": "require-corp" }
]}]}
```

Same two headers in `vite.config.ts` under `server.headers`, which replaces upstream's
hand-rolled `scripts/devserver.js`. Auto-deploy on push to `main` via Vercel's Git
integration; PR previews give every change a shareable URL. Models are served from the
`webnn/` HuggingFace org rather than bundled, keeping the deploy small.
